# Pulse: a live observability and incident console

Pulse is a Datadog/Grafana-style console that runs entirely in the browser on a **deterministic, simulated backend** in a Web Worker. Everything you see (metrics, logs, alerts, deploys, the outage) is generated by a seeded simulator. **None of it is real telemetry.**

```
npm install && npm run dev      # http://localhost:5185
npm test                        # 30 vitest unit tests
npm run build                   # tsc --noEmit && vite build
npm run e2e                     # real-Chrome mission walkthrough (needs the dev server running)
npm run measure                 # performance numbers below
```

## Try it
A guided mission, "Investigate the outage", opens on first run. Its 8 steps tick themselves off from real state, not clicks on a checklist: brush-zoom the latency spike, filter logs with `level:error service:<culprit>`, click a value in a log row to add a chip, click the deploy flag, create an alert rule from a chart, watch it fire, declare an incident, roll back, resolve and copy the post-mortem. Every step has a "Show me" button. "Start a new simulated incident" re-runs the simulator with another seed (different culprit service, timing and noise).

Other things to poke: drag to brush, shift-drag to pan, wheel to zoom (cursor anchored), double-click to reset, arrow keys / `+` / `-` / `End` / `0` on a focused chart, Live/Paused, log/linear toggle, legend toggles, hover a series (highlights in every chart), hover/click services in the topology map, `Ctrl/Cmd+K`, the copy-link button (the URL hash restores the exact view).

## Architecture

```
src/
  shared/    protocol.ts (typed worker messages), types.ts, prng.ts, scenario.ts (seeded story),
             gen.ts (metric + log generators), logTemplates.ts
  worker/    sim.worker.ts  generation in chunks, live ticks, alert evaluation, log queries
  engine/    pure, DOM-free, unit-tested:
             query/{tokenizer,parser,evaluator,suggest}.ts, downsample.ts, alerts.ts, urlState.ts, trace.ts
  render/    Canvas 2D chart engine (no React): layer.ts, timeseries.ts, histogram.ts,
             interaction.ts, axis.ts, scheduler.ts, theme.ts
  state/     store.ts (tiny external store), data.ts (typed-array data plane), sim.ts (worker client),
             actions.ts (all transitions), mission.ts (tour predicates), health.ts
  ui/        React components (thin wrappers around the renderer)
```

**Worker.** One worker owns the simulation. At boot it generates 28 h of 1 s samples (100,800 points) for 8 services x 8 metrics, plus 240,000 log lines, in per-service / 20k-row chunks that are posted as transferable typed arrays so the UI can show progress. It then ticks at 4 simulated seconds per real second, appending a sample per series plus ~12 log lines per tick, evaluating alert rules and posting alert transitions. Log queries also run in the worker, which returns a `Uint32Array` of matching row indices plus histogram buckets and a `performance.now()` timing. The protocol is a discriminated union in `shared/protocol.ts`.

**Determinism.** `makeScenario(seed)` picks the culprit service, deploy time, an error burst and a memory-leak ramp. Metrics use per-service sequential PRNGs with AR(1) noise, so the same seed always tells the same story (tested). Rolling back the bad deploy in an incident feeds a fix timestamp into the effects function, so metrics genuinely recover.

**Decimation.** The UI thread keeps the full arrays; the charts never draw raw points when zoomed out. Per frame, each series is reduced with a **min/max bucket** pass with one bucket per plot pixel (output at most 2 x width + 2 points), emitted in index order so spikes and dips can never be lost (tests assert exact global and per-bucket min/max preservation and the output bound). An LTTB implementation drives the service-tile sparklines. The renderer uses two canvases (heavy base layer, cheap crosshair/tooltip overlay), is DPR-correct, skips off-screen charts via `IntersectionObserver`, and a single shared `requestAnimationFrame` loop runs only when something is dirty.

**Query language.** Hand-written tokenizer, recursive-descent parser, and a compiler to a row predicate over typed columns.

```
query   := or
or      := and ( OR and )*
and     := unary ( [AND] unary )*          adjacency is an implicit AND
unary   := (NOT | '-') unary | primary
primary := '(' or ')' | FIELD ':' value | FIELD op number | "string" | word
op      := > >= < <= = !=
fields  := service level region host (enums, '*' wildcards)  status latency (numbers)  msg (text)
```
Example: `service:checkout level:error latency>500 "timeout" AND NOT region:eu`. Keywords are only keywords in upper case. Errors carry source positions (syntax and semantic, e.g. unknown field or value with a "did you mean" hint) and are rendered under the input with a caret. Syntax highlighting is an overlay over a transparent input; autocomplete is a pure function `(text, caret, schema)` surfaced as an ARIA listbox. Filter chips are AST nodes AND-ed onto the typed query.

**Alerts.** `stepRun` is a pure state machine (fires after the condition holds continuously for the window, resolves on the first clear sample). The worker steps it every sample; the rule editor's live preview replays the same function over the visible range (a test proves both give identical intervals).

**URL state.** `encodeState/decodeState` (round-trip tested, hostile input sanitised) serialise tab, seed, live span or absolute range, query, chips and scale into the hash.

## Measured performance
Apple M4 (10 cores, 16 GB, macOS 24.6), Chrome 154 headless, 1440x900 @2x, Vite dev server. Run `npm run measure`; numbers vary run to run. `performance.now()` in Chrome is quantised (0.1 ms), so sub-millisecond figures are coarse.

| What | Result | How |
|---|---|---|
| Simulator boot | ~340 ms for 6.4M metric samples + 240k logs | worker-side `performance.now()` around generation |
| Min/max decimation | median 0.1 ms, p95 0.3 ms for 100,806 points to 2,402 | 300 runs in the page on a real series |
| Frame cadence under interaction | median 16.7 ms, max 16.8 ms, 0 of 931 frames over 20 ms | rAF deltas during 60+60 wheel zooms, a 120-step shift-drag pan and a 200-step crosshair sweep, full 28 h range, 7 charts |
| Chart draw cost | median 1.2 ms, p95 8.1 ms, max 11.2 ms per frame (all dirty charts) | `performance.now()` around the shared flush |
| Points drawn | at most 22,410 decimated points per frame (vs 100,806 per series per chart) | max `pointsLastFrame` sampled during the interaction |
| Log query | 1.9 to 11.2 ms median, 240,898 rows scanned, 6 queries from `level:error` (3,213 matches) to a 4-clause query (133 matches) | worker `performance.now()`, 12 runs each |

The headless rAF is capped at 60 Hz, so "no frame over 20 ms" is the meaningful figure, not the median.

## Tests
`npm test` runs 30 unit tests: tokenizer, parser (precedence, errors with positions, never throws), evaluator (including semantic errors), autocomplete, downsampling (min/max preservation, bounds, ordering), alert evaluation, URL round-trip, simulator determinism. `npm run e2e` drives Chrome with real mouse and keyboard through the full mission and asserts each step completes (35 checks), then captures the screenshots.

## Limitations (honest)
- All data is simulated; the "backend" is a worker. There is no ingestion, auth, persistence or multi-user state. Incidents live in memory (mission progress and saved queries use localStorage).
- Live simulation is capped at about 2.7 hours of runtime (preallocated buffers), logs at 420k rows; the default 28 h metric history and 6 h log history are fixed.
- Free-text search matches the message templates only, not arbitrary fields. Traces are derived from the trace id, not stored spans.
- Charts assume uniformly sampled 1 s data; the decimator would need timestamps for irregular series.
- Timestamps are UTC. Touch gestures: horizontal drag brushes, there is no pinch-zoom.
